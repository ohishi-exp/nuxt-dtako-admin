## 2. 6 指標それぞれ — デジタコ運行から出せるか

### 2.1 前提: `dtako_events` は 3 層構造で、層をまたがなければ二重計上は起きない

issue の「**`dtako_events` の区間は入れ子なので素朴な合計は二重計上になる**」という
懸念は正しい。**ただし入れ子ではなく「並行する 3 つの層」だった** (実測)。

| 層 | state | 性質 |
|---|---|---|
| **A: 作業区分** | `運転` `積み` `降し` `休憩` `休息` `待機` | **運行スパンを過不足なく敷き詰める** |
| **B: 道路種別 × 積空** | `一般道実車` `一般道空車` `専用道` `高速道` | 同じく**過不足なく敷き詰める** |
| **C: 重畳マーカー** | `アイドリング` `連続運転` `一般道速度オーバー` `高速道速度オーバー` `専用道速度オーバー` | A/B と**自由に重なる**。合計してはいけない |
| **D: 境界** | `運行開始` `運行終了` | 長さ 0 |

**実測 (76 driver-month = 38 名 × 2 か月、運行 延べ 約 700 本):**

- 層 A の区間を運行ごとに時刻順に並べると、**隣接ペアの「前の終了 == 次の開始」が
  100% 成立** (重なり 0 件・隙間 0 件)。層 A の総和 = `運行開始 → 運行終了` のスパンに
  **秒まで一致**。
- 層 B も同じく重なり 0・隙間 0・総和 = スパン。
- **`待機` を層 A に入れないと破れる** — 入れないと 38 名中 4 名 (`1068` `1211` `1368`
  `1584`) で「隣接していないペア」が出る (`1368` は 14 か所)。`待機` を足すと **0 名**。
  この 1 語で層 A の定義が確定した。

⇒ **二重計上は「層をまたいで足したとき」だけ起きる。層 A の中だけで足せば起きない。**

### 2.2 判定表

| 指標 | 出せるか | 出し方 / 出せない理由 |
|---|---|---|
| **運転** `drivingMinutes` | **◎ 出せる** | 層 A の `運転` を暦日にクリップして合計 |
| **荷役** `loadingMinutes` | **◎ 出せる** | 層 A の `積み` + `降し`。**`待機` を足してはいけない** (§2.4) |
| **年度累計** `fiscalCumulativeMinutes` | **△ デジタコからは出せない。別の作り方でなら出せる** | これは**拘束**の 4月〜前月累計であって運行イベントの集計ではない。作るなら「保存済みの月次 拘束合計を 4 月から積む」。ただし**いま画面が出している拘束は打刻由来**なので、そうやって作った値は theearth の値と**構造的に一致しない** (§2.5) |
| **拘束上限** `restraintLimitMinutes` | **× 出せない** | 労使協定の値 (275h)。運行データのどこにも無い。**マスタ化するしかない** |
| **当月超過** `excessRestraintMinutes` | **○ 上限さえ与えれば出せる** | `max(0, 拘束合計 − 上限)`。デジタコは不要。**むしろ今が壊れている** (§3.2) |
| **平均運転9h超過** `avgDriving9hOverCount` | **× いまは出せない** | theearth の `前運転平均` / `後運転平均` の定義を**再現できなかった** (§2.6) |

**全部は出せない。** 「出せる」のは 6 のうち **運転・荷役** の 2 つ、
**上限をマスタで与えれば 当月超過** を足して 3 つ。年度累計は「別物として作り直す」判断が要り、
平均運転9h超過は**定義が未確定**。

### 2.3 実測: 運転・荷役は theearth と何分違うか

```
        n    median|Δ|   p75    p90     max    |Δ|<=10分
2026-06  38
  運転           4.5分   8.9   150.1   280.6    30/38
  荷役           1.6分   3.6    34.6   179.2    34/38
2026-05  38
  運転           5.0分   8.9   118.5   783.5    30/38
  荷役           1.5分   4.1   165.3   621.6    32/38
母数の規模: theearth の月間 運転 の median は 10224 分 (2026-06) / 9204 分 (2026-05)
```

**median 4.5 分 / 1 万分 = 0.045%。** 大半は theearth が日別に「H:mm」へ丸めることで
積み上がる誤差 (勤務日 26 日 × ±0.5 分) で説明が付く大きさ。

**外れ (|Δ運転| > 10 分) は毎月 8/38 (21%)。ただし外れる顔ぶれは月ごとに入れ替わる:**

```
2026-06 の外れ: 1071 1387 1517 1584 1634 1652 1667 1726
2026-05 の外れ: 1368 1387 1496 1556 1652 1656 1667 1684
両月とも外れ  : 1387(+16.5 / +10.3 — 境界値) 1652 1667
```

```
  cd   Δ運転(06)  Δ運転(05)
 1517    -165.5      -6.7     ← 06 だけ
 1584    -150.1      +9.8     ← 06 だけ
 1726    -141.2      -4.6     ← 06 だけ
 1556      +7.4    -783.5     ← 05 だけ
 1368      -1.9    +217.0     ← 05 だけ
```

**これは「特定の乗務員/車輌では手法が効かない」形ではない。** 構造的な欠陥なら同じ人が
毎月落ちる。**落ちる人が毎月入れ替わるのは「片方の時点が古い」型の症状**で、
測定条件 (§0) の 5 週間ずれ + 後からの編集 (乗務員の付け替え / イベント分類の編集 —
`kintai-ops` skill が「alc が古くなる原因は 2 つとも後からの編集」と書いているのと同型)
と整合する。**ただし今回それを確定はさせていない** — 確定には同時点測定 (§4) が要る。

### 2.4 `待機` は荷役ではない (実測で確定)

`荷役 = 積み + 降し + 待機` にすると壊れる:

```
2026-06  1368: 待機 540.9分  Δ(積+降) +1.8分 → Δ(積+降+待機) +542.7分
         1211: 待機  44.3分  Δ(積+降) -1.8分 → Δ(積+降+待機)  +42.4分
2026-05  1368: 待機 307.5分  Δ(積+降) +1.0分 → Δ(積+降+待機) +308.6分
```

**`待機` は拘束には入るが、theearth の運転にも荷役にも入っていない**独立のカテゴリ。
`待機` を持つ乗務員は 38 名中 4 名と少ないので、**median だけ見ていると気づけない**
(median は 1.6 → 1.6 でほぼ動かない)。当該 4 名を名指しで見て初めて分かった。

### 2.5 年度累計は「同じ名前の別物」になる

`fiscalCumulativeMinutes` は CSV の「4月～M月 累計拘束時間」行。つまり
**theearth が自分の拘束をその年度ぶん積んだ値**であって、デジタコの生イベントから
出るものではない。

一方**画面の「拘束合計」列は打刻 (timecard / kosoku-daily) 由来**に切り替わっている
(2026-07-28 決定)。**同じ行に「打刻由来の当月拘束」と「theearth 由来の年度累計」が
並んでいるので、いま既に足し算が合っていない。**

実測 (2026-06、両ソースに居る 68 名):

```
theearth の月間拘束   median 15058 分
timecard の月間拘束   median 20956 分     差 median +4540 分 (75 時間)
```

⇒ **年度累計を作り直すなら、拘束の正 (= 打刻) と同じ系列で積み直すしかない。**
そうすると数字は theearth の値から大きく動く。**これは「一致させる」対象ではなく
「定義を変える」判断**で、ユーザーの承認が要る (§6-Q3)。

### 2.6 平均運転9h超過は再現できなかった (陰性の結果)

`summarizeRestraintDriver` は CSV の `前運転平均` / `後運転平均` 列がそれぞれ 9:00 を
超えた回数を数えている (だから theearth が計算済みの値を読んでいるだけ)。
デジタコから出すには**その 2 列の定義を再現する必要がある**。

暦日ごとの運転時間から作れる自然な定義を **6 通り**試したが、**どれも合わない:**

```
定義                                       38名中の一致数   theearth>0 の 29 名だけ
前後を別々に数える (現行実装の写し)                 11/38            2/29
前後を別々・勤務日のみ                          11/38            2/29
両方超過した日を 1 回 (改善基準告示の本来の形)          9/38            0/29
両方超過・勤務日のみ                            9/38            0/29
前後を別々・>= 9h (境界を含める)                  11/38            2/29
前後を別々・分に丸めてから平均                      11/38            2/29
```

一致した 11 のうち 10 は「両方 0」の自明な一致。**`theearth` が 1 以上を出している 29 名で
合ったのは 2 名だけ** = 実質不一致。ずれの向きも一定でない (`1071` 19 対 12 でこちらが多い、
`1068` 2 対 4 でこちらが少ない) ので、単純な off-by-one でもない。

⇒ **theearth の「前/後運転平均」は暦日の運転時間の 2 日平均ではない。**
運行 (勤務) 単位か、別の起算のはず。**現時点では出せない。**
`summarizeRestraintDriver` の doc comment 自身が「theearth プレビューの値との突合は
staging 検証項目」と書いていて、**この repo は元々この列の定義を確かめていない。**

## 3. 切り替えたときに金額は動くか

### 3.1 結論: **6 指標だけを差し替える限り、1 円も動かない**

`computeWageRow` (`restraint-wage.ts:904`) が `summary` から読むのは

```
summary.days (→ classifyMonth)   summary.workingMinutes   summary.restraintMinutes
summary.driverCd   summary.driverName   summary.branchName
```

だけ。**6 指標は `restraint-wage.ts` に 1 回も現れない。陽性対照つきで測った:**

```
restraint-wage.ts に出現する回数
  drivingMinutes 0   loadingMinutes 0   fiscalCumulativeMinutes 0
  restraintLimitMinutes 0   excessRestraintMinutes 0   avgDriving9hOverCount 0
  (ついでに over15hDays 0 / maxDailyRestraintMinutes 0)
─ 陽性対照 (金額に効く項目) ────────────────
  workingMinutes 2   restraintMinutes 1   days 14   branchName 7   driverCd 15
```

grep が生きていること自体は陽性対照で確認済み。**「どの月の誰がいくら動く」は
「誰も動かない」が答え。**

### 3.2 ★ ただし条件が 2 つある

**(a) 「三源目」を行そのものの source にしたら動く。**

2026-06 の内訳:

```
theearth に居る          112 名
timecard に居る           96 名
両方に居る (埋め戻し対象)   68 名
theearth にしか居ない      44 名   ← この人たちは 拘束・実働・日別 も theearth 由来 = 金額の入力
timecard にしか居ない      28 名
```

`fillTheearthOnlyMetrics` が働くのは **68 名だけ**。残り **44 名 (39%)** は行ごと
theearth 由来で、`mergeSummarySources` が `source: "theearth"` として素通ししている。
**ここに三源目を挿すと 44 名の金額が動く。**

⇒ **#612 の実装の受け入れ条件に「6 指標**だけ**を差し替える。`days` /
`restraintMinutes` / `workingMinutes` には触れない」を明記すること。**
検証は golden テスト (`restraint-wage-golden.test.ts`) が既にあるので、
**同じ入力で `computeWageRow` の出力がバイト単位で不変**であることを陰性対照として測れる。

**(b) いま画面の「当月超過」は既に嘘をついている。#612 はそれを直す機会。**

`fillTheearthOnlyMetrics` は `excessRestraintMinutes` を **theearth の値のまま**
コピーする。その値は **theearth の拘束**から計算されたもの (`summarizeRestraintDriver`:
`max(0, restraintMinutes − restraintLimitMinutes)`) なのに、**同じ行に表示される
「拘束合計」は打刻由来**。読者が検算すると合わない。

実測 (打刻行が健全なものだけに絞る = **勤務日 ≥ 15 かつ 打刻エラー 0 日**。
勤務日が 2〜7 日で拘束 500h 超といった打刻側の既知の異常行を母数から外すため):

```
2026-06  対象 13 名 / 両方に居る 68 名
   表示の当月超過 != max(0, 表示の拘束合計 − 16500) : 8 名
   median|Δ| 883 分 (14.7h)   max 3896 分 (65h)
   うち「超過 0 と表示しているが実際は超過している」: 3 名

2026-05  対象 14 名 / 68 名
   同上 : 10 名   median|Δ| 368 分   max 2861 分
   うち「超過 0 と表示しているが実際は超過」: 5 名
```

**逆向き (超過を出しているが実際は 0) は 0 名** — つまり**一方向に見落とす**壊れ方。
改善基準告示の超過表示としては誤り。金額ではないが、**#612 が「上限だけマスタから
与えて超過を再計算する」だけで消える。**

なお `overlayGcpDayTimes` (`gcp-day-summaries.ts:237`) は同じ再計算を**既にやっている**
(`summary.restraintLimitMinutes` から `max(0, restraintMinutes − limit)`)。

整合していない。** 直し方の実物は既にリポジトリの中にある。

## 5. どちらのソースで出した値か、画面から読めるか

**既存の流儀 (#609) はこう:**

- `RestraintDriverSummary` に `backfilledFromTheearth?: readonly TheearthBackfillKey[]`
  を持たせる。**埋め戻しが無い行ではキー自体を足さない** (空配列と unset を分けない)
  — 「打刻由来で null」「theearth にも無くて null」を潰さないため。
- `RestraintWageMonthlyTable.vue` が該当セルに **violet の 1.5px ドット** + `title`
  (`BACKFILL_TITLE`)、1 行でも埋め戻しがあれば表頭に凡例。
- **行全体が theearth 由来の場合はドットを出さない** — それは `WageReportRow.source` の話、
  という切り分け (`RestraintWageMonthlyTable.vue:38-40` の doc comment)。

**提案 (この流儀を壊さない):**

1. `backfilledFromTheearth` は**そのまま残す**。並べて **`backfilledFromDtako?: readonly
   TheearthBackfillKey[]`** を足す。同じ「埋めるものが無ければキーごと足さない」規約。
2. ドットの色を分ける: **violet = theearth (拘束時間管理表) / sky = dtako (運行イベント)**。
   形は変えない (既存の 1.5px 丸)。
3. 凡例は **2 行**にする。`hasAnyBackfill` の判定を `theearth` / `dtako` それぞれで持ち、
   **その月に実際に出ている印だけ**を凡例に出す (無い印の説明を出さない)。
4. `BACKFILL_TITLE` は 1 本のままにしない。**理由は共通・結果は指標ごとに違う**ので、
   dtako 側は「デジタコ運行イベント (運転/積み/降し) から算出した値です」と別文にする。
   1 本にすると片方で嘘になる。
5. **同じ指標に両方の印が出ることは無い** — 埋め戻しは「まだ null のものだけ」なので
   先勝ち。**どちらを先に当てるかが表示の意味を決める**ので、優先順を決めてコードに
   書く。**提案: dtako を先、theearth を後** (dtako の方が鮮度が高い。§2.3 の
   「無人で当日まで入っている」を根拠にする)。

**CSV / 印刷にも同じ区別が要るか** は未決 (§6-Q4)。今の CSV (`restraint-wage.vue:2294`)
は値だけで由来を持っていない。

## 付録: 再現手順 (read-only、認証不要、作業 PC から)

```bash
# theearth 側 (拘束時間管理表 由来の写し)
curl -s "<オンプレ ichiban の内部 URL>/api/restraint/wage-source?comp=27324455&month=2026-06"

```

- `?comp=` は必須 (無いと 400 `missing field comp`)。
- 1 リクエスト約 16 秒。**並列 4 本で 502 が出た** ので 3 本以下か逐次で。
- 集計は `source == "dtako_events"` の行だけを使い、`state` が
  **`運転` `積み` `降し` `休憩` `休息` `待機`** のものを暦日にクリップして合計する。
  `アイドリング` `連続運転` `*速度オーバー` `一般道*` `専用道` `高速道` は**足さない**。
