# オンプレ vs Supabase の勤怠差を画面で確認し、両側の取り直しを押せるようにする — 計画 (Refs #615)

## 背景

勤怠の日別サマリは 2 か所にある。**オンプレ**は社内 MariaDB を毎回生読みするライブ計算、
**GCP (Supabase)** は運ばれてきた打刻を畳んだ `kintai.day_summaries`。
**同じ binary の同じ `kosoku` 実装**なので原理的には同じ値になるはずだが、実測で差がある。

## 調査結論 (5 点)

1. **原因は画面から判定できない。** 紙タイムカード突合 (#610) には `cause` 機構があるが、
   あれは**紙と打刻が別ロジック**だから型が作れた。オンプレと GCP は同じ実装なので、
   差は「**入力が違う**」= **2 つの DB の中身の差**でしかない。⇒ `cause` の移植はしない。
2. **nginx vs rust の突合は収束済み** (2026-06 / 117 名: 未説明 **3 日**、
   `cause_days` は lunch 486 / ferry 51 / punch-head 12 ほかで 570 日超を分類)。
   #610 の機構は**役目を果たし終えている**。
3. **単純な stale ではない。** `run_kintai_recalc` の dry 実測 (2026-06) で
   `stale.drivers: 0` / `drivers_written: 0` — 畳み直しても 0 行しか変わらない。
4. **代わりに観測値が出た。** `warnings: "dtako 入力欠け: 乗務員12名の末尾が16日超"` /
   `unko_diff_gcp_only_in_month: 417` (GCP にしか無い運行) / `unko_diff_total: 0`。
5. **押しても直る保証がある対象は実データで 0 件。** `get_rest_diff` の `mismatch_total` が
   **3 ヶ月連続 0**。表に出る 239〜243 件は全部 `dtako_missing` で、rust 側のコード自身が
   「押しても直る保証が無いので混ぜるな」と書いている側。
   **打刻そのものは無人で直せない** (`TimeCardDstateController` は在るが認証+CSRF 必須)。

## 決定 (1〜4)

1. **「推定原因」ではなく「観測できる状態」を並べる** — 差の 5 区分 / stale か /
   fold の warnings / GCP-only 運行の件数。**原因を断定しない**。
2. **差の横に「どの操作で直りうるか」を出す** (処方の候補)。
   **「押せば直る」とは書かない** — 保証の有無を必ず併記する。
3. **取り直しは 3 口、既定は dry-run。** 押す前に「何件変わるか」を見せる二段階。
   口は **`/restraint-api/*` に viewer 認可 (auth-worker introspect)** で足す
   (`/kintai-relay/*` は機械用でブラウザにシークレットを配れないため)。
   recalc のページングは画面が回す (`max_drivers` は 50 程度に落とす —
   150 で Cloudflare 100 秒上限に当たる実測がある)。
4. **取得は月全体を 1 回、絞り込みは手元で** — 実測で `rest-diff` の driver 絞り込み
   (12.2 秒) が月全体 (0.32 秒) より遅い。
